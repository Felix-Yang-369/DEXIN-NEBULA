# 站内通知与操作审计

## 1. 目标

站内通知解决“谁需要在何时处理什么”，操作审计解决“谁在何时对什么执行了什么
动作”。二者是跨业务模块共享的基础能力，不为请假、报销或采购分别建设。

## 2. 通知模型

`notifications` 按接收员工保存消息。当前自动产生：

- 新申请进入审批人的待办节点
- 审批进入下一位处理人的节点
- 申请已通过、退回、驳回或撤回

安全边界：

- 员工只能读取自己的通知。
- 已读状态必须通过受控数据库函数修改。
- 通知正文只包含必要摘要，不保存请假事由、报销说明、金额或票据内容。
- 跳转地址只允许站内相对路径。
- 当前不通过邮件或企业微信发送经营和员工隐私数据。

## 3. 审计模型

`audit_logs` 当前记录请假和通用审批的动作事件：

- 操作人
- 动作
- 业务对象类型和 ID
- 前后状态
- 操作时间

审计日志不保存审批意见、请假事由、报销说明或附件内容。记录由数据库触发器生成，
业务页面没有新增、修改和删除权限。

只有当前组织的系统管理员可以读取公司级审计记录。管理员权限只允许查看，不表示
可以代替业务负责人执行审批。

## 4. 当前限制

- 第十个迁移只对迁移执行后的新动作生成日志，不回填历史审批。
- 当前只有审批流程接入通知和审计，员工、客户、产品、库存及财务写操作后续接入。
- 暂未实现通知偏好、消息保留期限、审计导出和异常行为告警。
- 暂未接入企业微信消息。

## 5. 验收重点

1. 员工提交申请后，直属负责人收到一条待办通知。
2. 负责人同意后，下一节点负责人收到通知。
3. 申请结束或退回后，申请人收到状态通知。
4. 其他员工不能读取或标记该通知。
5. 普通员工不能读取审计日志。
6. 管理员能看到操作人、动作、对象及状态变化，但看不到敏感正文。

## 6. 当前验收结果

开发环境曾完成事务内的合成数据冒烟测试：

- 一笔合成测试报销经过直属负责人和财务两个节点后通过。
- 产生 3 条通知：负责人待办、财务待办、申请人完成通知。
- 产生 3 条审计：提交、负责人同意、财务同意。
- 测试事务最终回滚，测试申请、通知、审计和临时角色均未保留。

可重复执行的测试脚本位于
`supabase/tests/expense_notification_smoke.sql`。
