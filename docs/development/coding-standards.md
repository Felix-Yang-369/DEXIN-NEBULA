# 开发与安全规范

本文记录日常开发、数据、安全和交互规则。项目入口见 [README.md](../../README.md)，架构边界见 [architecture.md](./architecture.md)。

## 开始任务前

1. 阅读 README，确认当前版本、部署状态和未完成边界。
2. 查看相关路由、业务模块、SQL 迁移和测试。
3. 检查工作区现有修改，用户改动视为用户资产。
4. 检查开发服务器是否已经运行，避免重复启动和端口漂移。
5. 涉及 Supabase 或生产环境时，确认目标项目和环境。
6. 涉及身份、权限、金额、库存、员工隐私或生产数据时，先明确风险与回滚方式。

## 依赖与源代码

- 使用 npm，不混用 pnpm 或 yarn。
- 新增依赖前确认现有依赖无法解决问题，并说明运行环境影响。
- 依赖变化必须同步提交 `package-lock.json`。
- 不提交 `node_modules`、`.next*`、`.env*`、数据库备份、真实名单或临时文件。
- 大改动拆分为清晰提交；只有用户授权时才推送或发布。

## 数据库

- 所有结构变更新增 SQL 迁移，不修改已执行迁移。
- 核心表保留稳定主键和 `organization_id` 边界。
- 金额使用 PostgreSQL `numeric/decimal`，JavaScript 展示前显式转换。
- 状态使用明确状态机，不使用互相冲突的布尔字段。
- 关键记录保留创建人、更新人、时间和审计信息。
- 员工、审批、财务和业务单据优先停用、作废或归档，不直接硬删除。
- 多表关键写入使用事务，避免库存、单据和财务余额不同步。
- 新增外键后检查查询索引。
- 迁移前确认数据库项目、备份、RLS 和回滚路径。

禁止在未知环境中直接执行生产数据清理、批量更新或破坏性迁移。

## 认证、权限与敏感数据

权限必须同时落实在页面访问、服务端操作、Supabase RLS 或事务函数、文件下载和字段级展示中。客户端隐藏按钮不等于权限控制。

身份证、银行卡、工资、合同、私人联系方式、客户价格、供应商结算、库存成本、利润、登录凭证和 API Key 均属于敏感数据。

- 敏感数据不得写入代码、日志、截图、测试快照或提交记录。
- `SUPABASE_SERVICE_ROLE_KEY`、`WECOM_APP_SECRET`、`DEEPSEEK_API_KEY` 只能在可信服务端使用。
- 服务端操作从会话读取员工身份，不接受客户端自报 `user_id`。
- 高风险操作必须明确确认、复核权限并记录审计。

## 财务与库存

- 销售确认不等于收入确认；当前应收在实际履约后形成。
- 采购订单不等于应付确认；当前应付在实际到货后形成。
- 核销不得让未核销余额小于零。
- 已核销单据不得随意修改类型和原始金额。
- 库存出库必须校验可用数量，并按批次效期处理。
- 调拨、盘点、履约、应收应付和凭证联动必须保证事务一致性。
- “预计毛利”与正式会计利润必须清晰区分。

## 德小馨 AI

- AI 继承当前账号权限，不是超级管理员。
- 回答标明来源；经营数据标明时间范围与统计口径。
- 不向未经批准的外部服务发送员工隐私或敏感经营数据。
- 申请、审批、付款、删除和修改数据必须经过用户明确确认，并由服务端重新校验权限。
- AI 服务异常时清晰降级，不影响核心业务系统。
- 对话、检索、Token 用量和高风险工具调用应可审计。

## UI 与交互

- 保持深蓝、青色、白色的企业科技风，不随意改成官网营销风。
- 高信息密度页面仍需提供清晰层级、搜索、筛选、空状态和错误状态。
- 桌面优先，但手机必须能完成登录、审批、查询和核心录入。
- 状态不能只依赖颜色表达。
- 表单必须包含标签、必填、校验、提交中、成功和失败反馈。
- 危险操作需要确认；自定义交互保留键盘和基础无障碍能力。
- 图片使用合理尺寸，不把大图直接放入列表。

## 服务端与 API

- 输入使用 Zod 或等价的严格服务端校验。
- 外部服务设置超时并限制重试。
- 不把数据库原始错误直接展示给用户。
- 写操作考虑重复提交和幂等性。
- 列表查询设置边界，避免无上限全表读取。
- 上传校验 MIME、扩展名、大小和访问权限。
- 错误日志保留追踪标识，但不包含凭证和敏感正文。
